Release notes
KrankyBear ProcessMiner -- cross-platform (Windows, Linux, macOS) process/system monitor

Future ideas:
Some day maybe, maybe never - defer for now
- Network use per process - shipped in 0.7.0 (ETW-based, Windows-only) -- no
  longer blocked on gopsutil, which still has no access to this itself.
- GPU resource use - Windows only since not readily available for Mac/Linux, maybe some day if we perceive value
- Process CPU affinity / priority controls -- scrapped rather than deferred: affinity has no real macOS support at all (Apple's affinity API is advisory-only, a non-starter on Apple Silicon), and priority is a rare power-user action for most people. Not worth the cross-platform inconsistency for the value.
- ntdll.dll hook-byte comparison (on-disk vs in-memory at known Nt* API entry points) + unbacked-executable-memory-region scan, Windows only -- the actual "prove an AV/EDR hook or malware patched something" signal, bigger than the thread-list-with-start-address-resolution shipped in 0.3.0. Revisit once that's proven useful in practice.
- Real CPU/motherboard temperature -- deliberately scrapped, not just deferred: the only reason tools like LibreHardwareMonitor can read this on Windows is a bundled ring0 driver (WinRing0.sys) for direct hardware-register access, and that exact driver's leaked/expired signing certificate has been abused in real BYOVD ransomware attacks (which is also why some AV/EDR flags it). Not worth bundling a kernel driver, signed or not, for a "nice to have" temperature reading. A headless CLI dump mode (one-shot snapshot to CSV/JSON and exit, for scripted/cron collection) was also considered here as a "some day" -- lower priority than the Future ideas above since nobody's asked for it yet.
- Disk S.M.A.R.T. health/temperature -- looked at this round (prompted by a
  request for BIOS/hardware info generally, which 0.7.0 does ship). No viable
  pure-Go Windows library exists: github.com/anatol/smart.go and its forks
  explicitly document Windows as unsupported (confirmed by reading the actual
  source, not assumed), and a web search turned up nothing more mature. The
  real options are hand-rolled WMI (MSStorageDriver_FailurePredictStatus --
  just a pass/fail boolean, no driver) or raw
  DeviceIoControl/IOCTL_ATA_PASS_THROUGH (full SMART attributes, more code) --
  either doable in the same style as this app's other *_windows.go files, but
  moved here rather than Future ideas: lower perceived value than the other
  items above it, on top of the extra hand-rolled work. Revisit only if a
  failing disk actually causes a real support case.

Version 0.8.0 - September 08, 2026
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✨ NEW "Activity" column in the Handles window -- per-handle read/write busyness indicator
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- Requested after using this app in place of Task Manager/Activity
  Monitor/procmon/Process Explorer while watching a large-file migration
  (Migrator: download -> stage to temp -> upload -> cleanup) and
  wanting to see, at a glance, which open handle was actually busy rather
  than just the process-level Disk R/W total.
- No platform exposes a real per-handle byte counter (confirmed by reading
  the actual gather code -- Windows' NtQueryObject, macOS's
  proc_pidfdinfo, and Linux's /proc/<pid>/fd all resolve type+path only,
  never I/O counts), so this is a best-effort proxy: every handle with a
  resolved filesystem path is stat()ed on each poll, and its size delta
  since the previous poll is turned into a KB/s rate -- the same
  cumulative-counter -> per-tick-delta pattern (including the same
  negative-delta clamp for a truncated/replaced file) already used for the
  process-level Disk R/W columns in procsampler.go.
- Renders as a small icon using the same Importance-driven color
  convention as the Signed/Notable columns: ○ idle (no growth since last
  poll), ● green/orange/red for light/medium/heavy write throughput
  (>0 / 512+ / 4096+ KB/s), blank for handles with no size signal at all
  (sockets, pipes, unresolved paths -- not a claim the handle is inactive,
  same "blank isn't an alarm" discipline used elsewhere in this app).
- Because reading a file doesn't change its size, this only lights up on
  writes -- a handle being read heavily (e.g. the migrator's source file
  during download) stays idle even while genuinely busy. Real per-handle
  read activity would need an OS-level per-handle I/O counter, which
  doesn't exist on any of the three platforms today; a possible
  Windows-only follow-up would correlate the existing ETW file I/O events
  by path instead, if this proves valuable enough to justify it.
- The Handles window also gained a type/path filter box (same
  substring-match convention as the child-process drilldown filter) and
  now self-refreshes while open instead of being a one-shot snapshot --
  throttled to a 3-second floor independent of the main "Refresh every"
  setting, and piggybacked on the process sampler's existing tick rather
  than a new ticker/goroutine, since re-listing handles does real
  per-handle syscalls on Windows and macOS and shouldn't scale with how
  fast the main table happens to be set to refresh.
- Confirmed against real activity on macOS: watched Migrator's own
  debug-log handle cycle through idle -> green -> amber -> red while it
  wrote during a large-file migration test. Windows handle/network
  behavior not yet verified this round.

🐛 FIXED a confusing raw ETW error when enabling Network/Disk I/O without Administrator rights
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- Found via real Windows testing this round: turning on "Show Network/Disk
  I/O" without running elevated surfaced ETW's own raw error verbatim --
  "EnableTraceEx2 failed for provider (...): The parameter is incorrect" --
  which is genuinely misleading. ETW's ERROR_INVALID_PARAMETER here is the
  real symptom of the modern SystemTraceSession path lacking
  SeSystemProfilePrivilege, not "Access is denied" the way a missing-
  privilege failure would naturally read, so nothing about the message
  pointed at the actual fix.
- Rather than pattern-match that unreliable text (the way wrapWPRError
  already does for wpr.exe's own, much more legible, Capture Trace errors),
  the new wrapETWStartError checks this process's real elevation state
  directly (isCurrentProcessElevated, already used elsewhere for admin
  detection) and, only when not elevated, appends a clear "close
  ProcessMiner and relaunch it as Administrator" instruction to the
  dialog. If the process is already elevated and the session still fails,
  the original raw error is left untouched rather than mislabeled.
- Scoped to the one place this failure actually reaches the user (the
  "Show Network/Disk I/O" checkbox's session start) -- the parallel ETW
  path for the 4th Interference Watch signal (Microsoft-Antimalware-
  AMFilter) hits the same underlying failure mode without Administrator,
  but that one is deliberately silent by design (a best-effort bonus
  signal, not something the user explicitly asked to turn on the way this
  checkbox is), so it was left as-is.


Version 0.7.0 - September 01, 2026
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✨ NEW "Net Send"/"Net Recv"/"Disk Latency" columns (ETW Phase 2 continued, Windows-first)
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- The genuinely hard remainder Future ideas has flagged since 0.5.0: real
  per-process network throughput and disk I/O completion latency, live, via
  ETW. New "Show Network/Disk I/O" checkbox (default OFF, unlike "Check
  Signatures" -- this one starts a real kernel-level tracing session, needs
  Administrator, so it shouldn't turn on silently) feeds three new columns.
  Confirmed empirically this round: github.com/tekert/goetw fully supports
  both the legacy singleton "NT Kernel Logger" (NewKernelRealTimeSession) and
  a modern per-provider mechanism (NewSystemTraceSession, Windows 11+) --
  the "unconfirmed support" caveat from earlier Future ideas notes is
  resolved either way.
- Network throughput turned out to be the easy half: classic TcpIp/UdpIp
  events carry the real subject PID directly in the payload. Disk latency is
  the hard half -- DiskIo completion events carry HighResResponseTime
  (latency, no manual Init/Complete IRP correlation needed) but no PID at
  all, only IssuingThreadId, since completion runs on an arbitrary kernel-
  stack thread. Attribution needs a TID->PID map, built by adapting the
  existing NtQuerySystemInformation(SystemProcessInformation) buffer-walk
  threads.go already uses for thread inspection (there scoped to one target
  PID) into a full-system scan, refreshed once per sample tick.
- Windows 11+ now uses the modern SystemIoProviderGuid per-provider session
  instead of the legacy singleton -- resolved after this had briefly shipped
  disabled (a prior real-hardware attempt found zero events and no
  documented field names to fix it from). A real capture on Windows 11 25H2
  produced a full netio-debug.jsonl, which showed every event still carries
  ProviderGUID {9E814AAD-3204-11D2-9A82-006008A86939} (the classic "NT
  Kernel Logger" GUID) with the exact same TcpIp/UdpIp/DiskIo Task names,
  IPV4/IPV6 Opcode names, and PID/size/daddr/saddr/dport/sport/connid/
  IssuingThreadId/HighResResponseTime properties the legacy path already
  decodes -- the modern mechanism turned out to be a different
  session/enablement API over the same underlying provider, not a
  differently-shaped one, so no decode changes were needed at all. Confirmed
  end-to-end: real moving values in Net Send/Net Recv/Disk Latency and the
  Connections window. Since it isn't the singleton kernel session, it also
  runs alongside Capture Trace freely on Windows 11+, exactly as the
  in-app error message already promised. Windows 10 still falls back to the
  legacy singleton mechanism, which does share Capture Trace's session --
  starting either while the other is active there shows a clear error
  explaining why, rather than one silently stopping the other mid-capture
  (the same class of corruption 0.5.0 fixed for exiting mid-save).
- One real bug caught via real-world testing on a Windows 11 box, elevated:
  the checkbox would silently stay checked with zero data in any column, no
  error, even during a genuine large download over gigabit fiber. Root
  cause: NewKernelRealTimeSession only configures EnableFlags in memory --
  unlike EnableProvider (used elsewhere in this app, e.g. avmonitor_windows.go's
  AMFilter session, which starts the session as a side effect), it has no
  path that actually calls the real StartTrace API. goetw's own Consumer.Start
  only opens a trace handle to an already-running session (confirmed in its
  source, which has a literal "// TODO: make is auto start the sessions"
  comment) -- so a handle was opened to a session that was never really
  started, and nothing ever arrived. Fixed with an explicit session.Start()
  call. A netio-debug.jsonl diagnostic log (same per-user folder as the
  watchlist) was also added alongside this fix: it records the real
  provider/task/opcode/property shape of every distinct kind of event
  actually captured, capped at 60 shapes, so a future schema mismatch (e.g.
  reviving the modern Windows 11 path) can be fixed from real captured data
  instead of guessing.
- Confirmed fully working end-to-end on real hardware after the fix: a
  genuine large file download (an AlmaLinux ISO, over gigabit fiber to an
  SSD) produced real, moving numbers in Net Recv and Disk Latency, filtered
  down to just the relevant browser process. Values show as brief flashes
  rather than a steady rate at that connection speed -- expected, not a bug:
  the 2-second sample tick often lands between bursts on fast-enough
  hardware, exactly the kind of thing worth confirming against real traffic
  rather than assuming.
- A second real bug, caught the same "capture real events, don't assume"
  way: the very first netio-debug.jsonl actually inspected (from a real
  Windows box, added below for the Connections work) showed the real
  classic-provider opcode names carry an address-family suffix this app
  never accounted for -- "SendIPV4"/"SendIPV6", "RecvIPV4"/"RecvIPV6", not
  the bare "Send"/"Recv" the code checked for. That means Net Send/Net Recv
  could never actually have populated on IPv4 or IPv6 traffic; the
  "confirmed... produced real, moving numbers" claim two paragraphs up
  reflects what testing appeared to show at the time, but with this bug
  in place, the more likely explanation is Disk Latency alone (DiskIo's
  "Read"/"Write" opcode names have no such suffix, and were never affected)
  was what actually moved, not Net Recv. Fixed by matching opcode names by
  prefix instead of exact string -- see the Connections entry below, which
  hit the identical bug and shares the fix.

✨ NEW "Show Connections" live per-process TCP connections list (ETW Phase 2 continued)
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- The other Future ideas item this release's ETW work opened the door to: a
  live, per-process list of TCP connections (local/remote address:port,
  direction) -- more like `netstat -b` than a throughput counter. New "Show
  Connections" button (gated behind "Show Network/Disk I/O", same session)
  opens a window that decodes the same TcpIp Connect/Accept/Disconnect
  opcodes the existing legacy session already carries, keyed by the kernel's
  own per-connection `connid` so a connection stays listed correctly across
  its lifetime rather than by address:port (which can be reused). Field
  names sourced from goetw's own generated kernel MOF definitions -- the
  same PID/saddr/sport/daddr/dport shape Send/Recv/DiskIo already use
  successfully, not a fresh guess.
- First real-hardware pass opened and ran without error, but real
  inspection of a captured netio-debug.jsonl from that same box (see the
  Net Send/Net Recv correction above) showed why rows weren't actually
  appearing: this code checked for opcode names "Connect"/"Accept"/
  "Disconnect" exactly, but the real events are named "ConnectIPV4"/
  "AcceptIPV4"/"DisconnectIPV4" (and an IPV6 counterpart for
  Connect/Disconnect -- no AcceptIPV6 sighting yet, but matched the same
  way regardless). Fixed by matching opcode names by prefix
  (`strings.HasPrefix`) instead of an exact match, the same fix applied to
  Net Send/Net Recv above -- one code change covers both. As a side effect
  this also decodes IPv6 connections, which turned out to need no special
  handling at all (the property names and formatting are address-family-
  agnostic) -- not the "IPv4 only, IPv6 is a known gap" limitation an
  earlier draft of this feature assumed.
- New "Connections" main-table column (same "Show Network/Disk I/O" gating)
  shows each process's live open-connection count -- prompted directly by
  testing this feature against a handful of same-named Chrome renderer
  processes: opening each one's own Connections window just to find which
  one actually had traffic was tedious, and a per-row count answers that at
  a glance instead. Shows "0" once something else about the process has
  been observed rather than staying blank, since a confirmed zero is real
  information (same distinction the other three columns already draw
  between "blank = nothing known yet" and "a real, checked value").
  Deliberately not click-sortable, matching Net Send/Net Recv/Disk
  Latency's own existing limitation (their live values live outside
  ProcInfo, which the sort comparator doesn't have access to) -- sorting by
  it to surface the busiest processes first is a natural next step if this
  turns out to matter beyond the testing convenience it was built for.
- A second real bug, caught by the "Connections" column above making the
  problem actually visible: a sustained large download (10Gb/s) never
  showed more than 0 open connections for the downloading process, even
  though real throughput was confirmed elsewhere. Root cause: Connect/
  Accept only fire at the exact moment a connection is established --
  a connection already open before "Show Network/Disk I/O" was turned on
  (a browser's kept-alive HTTP/2 connection, reused for a download started
  well after the tab was opened, is exactly this case) never produces one,
  so it stayed permanently invisible to a connections list built only from
  Connect/Accept/Disconnect, despite generating a continuous, very real
  stream of Send/Recv traffic the whole time. Fixed by opportunistically
  treating the first Send/Recv sighting of a not-yet-tracked connection as
  a substitute "this connection exists" signal (Send/Recv carry the same
  PID/address/port/connid fields Connect/Accept do) -- shown with a new
  "Existing" Direction value so it's clear the entry's existence, not which
  side dialed or accepted, is what's actually known. Guarded by a small
  known-connection cache checked from the ETW callback itself (not just
  deduped later) so this doesn't mean re-extracting every property on every
  single packet for the rest of a busy connection's life -- Send/Recv fire
  once per network packet, making this a genuinely hot path during exactly
  the kind of sustained high-throughput transfer that surfaced the bug.
- Polls every sample tick while open (like the children drill-down window)
  rather than snapshotting once like Threads/Handles, since the underlying
  data is itself continuously live, not something worth re-fetching on its
  own timer.
- Re-confirmed against real traffic after both fixes above is still the
  planned next step.

🐛 FIXED an elevated launch silently breaking persisted state
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- Found while adding the netio-debug.jsonl log above: an elevated Windows
  launch's window-title prefix ("Administrator: KrankyBear ProcessMiner")
  was also being used, unmodified, as the directory name for per-user app
  data. A colon is illegal in a Windows path component outside the drive-
  letter position, so this was silently failing every save under it on an

  stripping the "Administrator: " prefix before building these paths, in one
  shared helper now used by all three (watchlist, update-check cache, and
  the new debug log).

✨ NEW "Notify on Threshold Breach" (desktop notification)
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- New checkbox next to the Top CPU/Mem/Memory/Disk selects (off by default --
  a notification is a background-monitoring convenience, not something that
  should start firing unasked just because a threshold happens to already be
  set): sends a real desktop notification the instant a process newly
  crosses one of those same four thresholds. Reuses whichever thresholds are
  already configured rather than a separate set of notification-specific
  ones -- leaving all four at Off means this simply never fires.
- A rising-edge event, not "still above": a process that stays hot only
  notifies once, when it first crosses, the same "baseline, don't cry wolf"
  precedent Interference Watch's own unbacked-thread/new-module signals
  already established for their first check. Runs off every currently-
  running process, not just what the name filter or Parent-processes view
  happens to be showing, so a breach in a hidden row still notifies.

🔧 IMPROVED System tray icon now shows a hover tooltip (Windows, macOS)
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- Prompted by a real observation: other apps' Windows tray icons show the
  app name on hover, this one didn't. Fyne's own desktop.App interface
  genuinely has no tooltip setter (checked its definition directly --
  SetSystemTrayMenu/SetSystemTrayIcon/SetSystemTrayWindow is the whole
  list), but fyne.io/systray, the library Fyne's own desktop driver already
  uses internally for the tray icon, does expose one -- a documented no-op
  on Linux, real on Windows and macOS. Already an indirect dependency via
  Fyne itself; promoted to direct here, same as purego was for
  handles_darwin.go in 0.6.0. Uses the same appName the window titles do,
  so an elevated instance's tray tooltip says "Administrator: ..." too.
- Fyne's own SetSystemTrayIcon call works no matter when it's called
  because Fyne caches the icon and re-applies it once the tray is actually
  ready internally -- a raw systray.SetTooltip call made directly from
  application code has no equivalent caching, so it's set from a short
  deferred timer instead of inline, to give the tray time to actually
  exist first. Not yet verified against real hardware whether that delay

✨ NEW "Open Handles" window (per-process handle/fd listing, all 3 platforms)
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- New "Show Handles" button next to Show Threads/Watch for Interference/
  Check Signature: a one-off snapshot of every open handle/file descriptor a
  selected process holds and what it actually points to, where resolvable --
  promoted from Future ideas after the 0.4.0 Handles column surfaced a
  process with a surprisingly high count that the count alone couldn't
  explain. Same single-reusable-window, follows-the-selection window
  lifecycle as the existing Threads window (openOrRefreshThreadsWindow's
  pattern, copied line-for-line).
- Unlike Thread Inspection, every platform gets a real per-handle listing
  here -- the difference between platforms is implementation difficulty, not
  capability, so there's no Windows-only gating this time. Linux: plain
  /proc/[pid]/fd readlinks. macOS: proc_pidinfo (PROC_PIDLISTFDS) to list,
  proc_pidfdinfo (PROC_PIDFDVNODEPATHINFO) to resolve file-backed ones to a
  path -- this project's first use of github.com/ebitengine/purego (cgo-free
  dlopen/dlsym FFI), already an indirect dependency via gopsutil (which uses
  it for the exact same two libproc calls), just promoted to direct here;
  still zero cgo anywhere in this project. Verified for real against this
  project's own running process on the author's Mac, not just compiled --
  caught and fixed a real bug this way: proc_pidfdinfo kept returning ENOMEM
  for every vnode-type fd until the buffer struct's header was corrected from
  the small proc_fdinfo {fd, fdtype} pair (right for PROC_PIDLISTFDS's array)
  to the larger proc_fileinfo struct the detailed "withpath" calls actually
  expect -- the kernel's buffersize check rejects anything not exactly the
  right size, so the wrong header silently produced empty paths on every
  call rather than an obvious error.
- Windows is the hard one, as flagged in Future ideas: NtQuerySystemInformation
  (SystemExtendedHandleInformation -- deliberately the Ex class, not the
  legacy one the backlog named colloquially, since the legacy struct's PID
  field is a 16-bit USHORT, silently wrong above PID 65535) lists every
  handle system-wide; each one belonging to the target process is duplicated
  into this app (a handle value only means something inside its owning
  process's own table) and queried via NtQueryObject for its type and,
  where applicable, its path. File-type paths are translated from raw kernel
  form ("\Device\HarddiskVolume3\...") to a drive letter via the classic
  QueryDosDevice technique. Registry key paths show in raw NT form for now
  (not translated to HKLM/HKCU) -- a nice-to-have, not essential, deferred.
- The one real hazard here, exactly as Future ideas anticipated: resolving a
  handle's name can hang indefinitely for certain handle types (classically,
  a named pipe with no listener on the other end) -- no existing
  timeout-guarded-goroutine pattern anywhere else in this codebase to copy,
  so this is genuinely new infrastructure. Each name query runs in its own
  goroutine with a 100ms timeout; on timeout the row shows "(query timed
  out)" and a banner at the top of the window reports how many. The
  duplicated handle's closure is owned by that goroutine itself (closed
  whenever NtQueryObject actually returns, however late), not the caller --
  only a truly permanent hang leaks a handle/goroutine, and handles are
  queried sequentially so at most one such leak is ever outstanding at once.
  This is the same accepted tradeoff Process Explorer/Process Hacker
  themselves carry for this exact API -- Go, like any userspace caller, has
  no way to cancel a blocked syscall. Not yet verified against real hardware
  (needs the author's Windows box); flagged explicitly rather than assumed.

- Interference Watch now has a fourth detection signal, live: Windows
  Defender's own AMFilter minifilter intercepting a file a watched process
  opens -- the *other* meaning of "AV interference" (synchronous file-scan
  latency), which the original three signals can't see at all since they
  only look at what's happening inside the watched process itself, not at
  it from outside. Shown as a plain "⚠", never "🛑" (Defender doing its job

  time it happens rather than tracked against a baseline, since a file
  scan is a momentary event, not a persistent condition.

  Capture Trace -- via a real-time subscription to
  Microsoft-Antimalware-AMFilter using github.com/tekert/goetw (pure Go,

  research to scope correctly: a throwaway spike against the real hardware
  (subscribing to all four Antimalware providers, deliberately triggering
  activity via this project's own test/injection tooling, and inspecting
  ~18,000 captured events) found that only AMFilter's own FileScan task
  reliably carries the *scanning-triggered* process's real PID in the
  event header -- Microsoft-Antimalware-RTP's equivalent task has the
  *engine's* PID (MsMpEng.exe) instead, unusable for correlation without
  extra work, and Behavior Monitoring events (which, notably, captured
  this project's own injection tooling's exact OpenProcess call in loving
  detail) are far higher-volume and system-wide, out of scope for this
  pass.

  confirmed empirically (same requirement Capture Trace already has) --
  silently just doesn't activate if not running elevated, the same way
  the other three signals are silently inert on macOS/Linux. Not a
  deliberate user action with its own dialog, so no error is ever shown
  for "it didn't start" -- Interference Watch's other three signals work
  fine either way.
- The async ETW callback needed real synchronization to hand events to
  interferenceWatcher.check() (which runs on the main goroutine) without
  retrofitting a mutex onto that whole pre-existing, previously
  single-goroutine-only struct -- a small, separate, mutex-protected relay
  is the one new piece of state that's actually touched from two
  goroutines, confirmed race-free with `go build -race` on the real
  hardware (the same lesson Capture Trace's corrupted-.etl bug taught
  earlier this release, applied proactively here instead of found the
  hard way again).

  prior instance (simulating a crash) doesn't hang or crash a fresh
  launch -- it just silently fails to (re-)start the 4th signal for that

  here.

🐛 FIXED Capture Trace corrupting the .etl if you exit mid-save
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- Found the hard way via real-world testing: exiting ProcessMiner while
  Stop && Save's `wpr -stop` was still merging a trace corrupted the .etl
  (WPA refused to open the result). Root cause: quitApp's cleanup step
  unconditionally called `wpr -cancel` to tear down any still-running
  capture, but the code tracking "is a session running" didn't distinguish
  "recording" from "currently being saved" -- so quitting mid-save raced
  an actual `wpr -cancel` against the still-in-flight `wpr -stop`, and losing
  that race is exactly what corrupted the file. Fixed at the root: cleanup
  now only cancels a session that's just sitting there recording, never one
  mid-save or already finished -- letting a save that's already in flight
  finish on its own in the background even if you exit (wpr.exe is a
  separate process Windows doesn't tie to this app's lifetime), rather than
  actively sabotaging it. Needed a real mutex, not just careful ordering --
  this state is genuinely touched from two different goroutines (the save's
  own background goroutine and quitApp's main-goroutine cleanup), confirmed
  by rebuilding with `go build -race` on the real hardware.
- Also made the "Saving…" status impossible to miss while this window
  exists: red/danger-styled text explicitly warning not to exit until it
  finishes. Exiting still can't be blocked outright, so this is the
  practical mitigation on top of the actual fix above.

✨ NEW Thread inspection ("Show Threads" button, Windows-first)
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- Select a process and click "Show Threads" for a one-off snapshot of its
  threads. On Windows: TID, state, kernel/user CPU time, and each thread's
  start address resolved to "module.dll+0xOFFSET" -- or flagged "UNBACKED
  (possible injection)" when the address falls outside every one of the
  process's own loaded modules. That's the classic signal for reflective
  DLL injection or shellcode (the same technique Process Explorer/Process
  Hacker-style tools use), and the main practical ask behind this feature:
  verifying a customer's AV/security exclusions are actually configured
  as claimed, not just trusting that they are.
- This detects code *injected* into a process. It does NOT (yet) detect an
  AV/EDR *hook* patched into an otherwise-legitimate module like ntdll.dll
  -- that needs comparing in-memory bytes against the on-disk DLL at known
  API entry points, a separate, bigger piece of work noted in "Some day
  maybe" below.
- Windows implementation: NtQuerySystemInformation(SystemProcessInformation)
  for the thread list (thread start addresses aren't available via the
  simpler Toolhelp API), cross-referenced against the process's loaded
  modules via the classic Toolhelp module snapshot. Verified for real on
  Windows via SSH during development, not just compiled: a standalone test
  program confirmed thread states, start addresses, and module address
  ranges all resolve correctly against a real running process (including
  a documented NT quirk where the actively-querying thread's own start
  address reports as 0 -- handled as "unresolved", not misflagged as
  "UNBACKED").
- macOS/Linux: just a thread count for now. Resolving start addresses
  needs reading another process's memory, which needs an entitlement
  Apple doesn't grant ordinary third-party apps on macOS (SIP blocks
  task_for_pid), or root/CAP_SYS_PTRACE on Linux (Yama's ptrace_scope
  blocks it otherwise) -- a real platform gap, not something to code
  around. Best-effort, matching this app's general philosophy of being
  honest about what each OS actually allows rather than faking parity.

✨ NEW Interference Watch (continuous, on top of Thread Inspection)
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- Thread Inspection above is a one-off snapshot; this makes the same
  detection continuous and a lot more approachable for someone who isn't a
  Windows internals expert. Select a process and click "Watch for
  Interference" (next to "Show Threads"), or watch a whole directory --
  any process launched from it is covered automatically without
  reselecting it every time it restarts.
- Every process-list sample, each watched process is re-checked; a newly
  appearing UNBACKED thread (one that wasn't there the first time this
  process was checked) is logged as an event -- process, time, TID, start
  address -- and flags a "⚠" on that row in the main table. A thread that
  was already unbacked *before* watching started is recorded as the
  baseline and not reported, so watching an unusual-but-legitimate process
  doesn't cry wolf on the first check.
- Deliberately opt-in, not "watch everything": scanning every process this
  way would mean a Toolhelp32 module snapshot per process on top of the
  shared system-wide thread query every cycle -- fine for a handful of
  watched targets, not hundreds. Matches the actual ask: verify specific
  exclusions, not replace the AV.
- "Check for Interference" (View/Process menu, tray) opens the
  Interference Watch window: what's currently watched (with Remove), an
  "Add Directory to Watch…" picker, and the interference event log with
  Copy to Clipboard / Clear. Included in Hide All / Show All like every
  other secondary window.
- The one syscall NtQuerySystemInformation(SystemProcessInformation)
  already returns the whole system's thread list regardless of how many
  processes are being checked against it, so watching 1 target or 20 costs
  the same one call per cycle -- no repeat of this app's own earlier
  Status()-forks-ps-per-call mistake, just against a different call.
  Directory matching resolves each process's on-disk executable path
  (gopsutil's Exe()) once per PID and caches it, rather than re-resolving
  it for every running process on every tick.
- Windows-only, same constraint as the thread inspection it's built on --
  the watch list can still be built on macOS/Linux, but nothing is ever
  flagged there (the button and the window's "Add Directory" say so
  directly rather than silently doing nothing).
- Does NOT detect the *other* common meaning of "AV interference" --
  synchronous file-scan latency from a minifilter driver intercepting file
  I/O, which shows up as slow I/O on the target process while the AV's own
  process burns CPU, not as anything inside the target's own threads. That
  needs a different, ETW-based mechanism; not implemented here.

✨ NEW Interference Watch: second detection signal, new module loaded
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- The UNBACKED-thread signal above catches *reflective* injection (raw
  shellcode, no module ever loaded) -- malware's usual technique for
  staying off the module list. It deliberately does NOT catch legitimate
  AV/EDR hooking, which almost always uses ordinary LoadLibrary-based DLL
  injection instead, specifically because it *wants* its DLL visible, not
  hidden. Confirmed by live testing on a real Chrome process: a
  CreateRemoteThread-based shellcode stub read back with a generic,
  unresolvable start address in *both* ProcessMiner and Process Explorer
  (neither tool flagged it), while a LoadLibraryW-based DLL injection --
  the more realistic stand-in for how a real hook actually behaves --
  showed up cleanly via this new signal.
- Same watch list, same baseline/"newly appeared since watching started"
  semantics as the thread signal: a module already loaded before you
  started watching is the baseline, not reported. Logged as its own event
  ("new module loaded: <name>"), and flags the same "⚠" in the main table.
- Costs a second Toolhelp32 module snapshot per watched target per cycle
  (separate from the one the thread signal already takes internally) --
  simplicity over micro-optimization, still bounded by the watch-list
  size, not the system-wide process count.
- Two real bugs found and fixed via this live testing, both now verified
  against a real injected module on a real Chrome process:
  - The "⚠" indicator only stayed lit for the one sample tick a new module
    was first detected, then went dark even though the module -- and the
    interference it represents -- was still loaded. Now stays flagged for
    as long as the condition persists, matching the thread signal.
  - The new-module check was silently skipped whenever the *separate,
    unrelated* system-wide thread-list query failed on a given cycle, even
    though it doesn't use that data at all. Two consecutive live
    DLL-injection tests went undetected before this was caught -- fixed by
    no longer gating one detection path on the other's success.
- Also fixed: the Parent-processes children drill-down window's own "⚠"
  column wasn't wired to the flagged-PID state at all, so a recycled table
  cell could show stale leftover text from whatever column it last
  rendered (spotted via a screenshot showing PID/CPU/Private values
  bleeding into the "⚠" column).

✨ NEW Interference Watch: third detection signal, thread stack scan
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- Prompted by a real customer story: a Windows performance expert on the
  team caught a security team's undisclosed removal of required exclusions
  live, in front of the customer, by having them watch Process Explorer and
  scroll through threads and stacks -- "thread stacking," watching live
  call stacks for a security vendor's own code sitting in the call path.
  This is a coarse, address-scanning approximation of that technique: for
  each of a watched process's threads, reads the thread's entire committed
  stack region (via its TEB's StackBase/StackLimit -- no thread suspension
  needed, unlike reading live register state would require) and checks
  every pointer-aligned value against the process's loaded-module address
  ranges. A hit against a module that isn't part of Windows itself or the
  process's own files is reported.
- Deliberately reads the *whole* stack region, not just current call
  frames: a function that already returned doesn't clear the stack bytes
  it used, so this can still find evidence of a hook that ran and returned
  before the scan happened -- the same "recent history, not just this
  instant" property that lets a human watching stacks scroll by over time
  catch things a single live snapshot would miss, approximated here from
  one point-in-time read.
- Unlike the other two signals, this one has NO baseline: a hit is reported
  the first time it's ever seen for a watched process, even on the very
  first check, specifically because the point is finding evidence of
  something that may already have been happening before you started
  watching (the real customer case: exclusions had already been silently
  removed well before anyone looked). The "⚠" stays lit for as long as the
  module remains loaded, same persistence behavior as the new-module
  signal.
- A short, explicitly best-effort, user-extensible list of known AV/EDR
  module-name fragments (McAfee/Trellix, Symantec/Broadcom SEP, CrowdStrike
  Falcon, SentinelOne, VMware Carbon Black, Sophos, Trend Micro, Cylance,
  Palo Alto Cortex XDR) attaches a friendly vendor label when a hit
  matches -- an unmatched hit is still reported as an "unrecognized
  third-party module," not silently dropped, since the list is inherently
  incomplete (vendors rename/version/sometimes randomize module names) and
  an unlabeled hit is still worth investigating.
- This is a pointer-address scan, not true call-stack unwinding (what
  Process Explorer's own "Stack" button does) -- cruder, no call-frame
  structure, but far simpler, and answers the question that actually
  matters: is this vendor's code anywhere near this thread. Framed
  throughout the UI as "worth confirming with Process Explorer/Procmon,"
  not proof on its own.
- THREAD_BASIC_INFORMATION/TEB struct layout verified empirically against
  a real running process before shipping (same standard as the earlier
  SYSTEM_THREAD_INFORMATION work): TebBaseAddress resolved to a real
  address, and its UniqueProcess/UniqueThread fields matched the queried
  PID/TID exactly, confirming the field offsets.
- Windows-only, same constraint as the other two signals.
- Note from real testing: expect some genuinely benign "new module loaded"
  events alongside real findings -- large apps like Chrome delay-load
  Windows OS components on demand well after startup (e.g.
  Windows.Devices.Bluetooth.dll/BthRadioMedia.dll appearing the moment a
  Bluetooth-related API actually gets touched), not just at launch. Normal
  behavior, not a false detection -- the event log's real value is exactly
  this: building a sense of what's ordinary noise for a given process
  versus what's worth a closer look via the stack scan.

▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- The very first system sample after launch diffed disk/network byte
  counters against a zero baseline instead of skipping the first tick, so
  it reported the *entire* cumulative bytes read/sent since boot as a
  one-second "rate" -- a huge one-off outlier. Since the graphs auto-scale
  to their own visible max, that single spike dominated the axis (e.g.
  "473199313 KB/s") and squashed all real data into an invisible sliver
  until the outlier aged out of the buffer (2-5 minutes). CPU/Memory were
  never affected (fixed 0-100% scale, immune to this). Now the first
  sample only records a baseline and reports no rate, same as the
  per-process Disk R/W columns already did correctly.

✨ NEW System Info window
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
- A point-in-time summary (View menu / system tray): computer name and
  OS/platform/version/architecture, CPU model/cores/logical processors/
  speed, total memory, mounted disk volumes with size, and network
  adapters with type (wired/wireless), connected status, and WiFi signal
  strength where applicable.
- "Copy to Clipboard" button copies the whole summary as plain text --
  handy for a bug report or comparing against another machine.
- CPU speed shows N/A rather than a misleading "0.00 GHz" when gopsutil
  can't report it. Apple Silicon doesn't return a clean 0 for this --
  empirically it's some other meaningless counter (4 on an M4 Pro), which
  slipped past an initial `<= 0` check; fixed with a "no real CPU has run
  this slow in decades" floor (100 MHz) instead of exactly 0.
- "Copy to Clipboard" now confirms the copy happened -- the button relabels
  to "Copied to Clipboard ✓" and turns green for 2 seconds, since clicking
  it otherwise gave no feedback that anything had happened.
- Network adapter type is a name-pattern heuristic (wlan/eth/en0 etc.),
  not a guaranteed-accurate classification for unusual adapter names.
- WiFi signal strength: a real API on Linux (github.com/mdlayher/wifi,
  pure Go, no shell-out); a standard-tool shell-out on macOS
  (system_profiler) and Windows (netsh) -- neither OS has a comparably
  simple non-shell option (the real alternative is cgo+Objective-C or raw
  WLAN-API syscall struct marshaling, more code and more fragile than a
  one-line shell-out and text parse).
- Disk volumes are mounted filesystems (gopsutil's view), not raw physical
  disks -- there's no simple cross-platform API for the latter.
- The window now opens immediately with a "Collecting system info…" message
  and spinner while gathering runs in the background, instead of the whole
  app appearing to freeze until it's done. On macOS specifically, gathering
  can genuinely take 10+ seconds: system_profiler (used for WiFi signal
  strength) takes ~8s on its own regardless of -detailLevel, and there's no
  fast non-privileged alternative (wdutil info is near-instant but needs
  sudo; the legacy airport binary that used to be fast no longer exists on
  current macOS).
- Fixed: the loading message briefly rendered one character per line. It
  was wrapped in container.NewCenter, which sizes to the child's own
  MinSize -- an unconstrained wrapping Label's MinSize degenerates to
  almost nothing, so it wrapped at the narrowest possible width instead of
  real word boundaries. A plain VBox gives it the container's full width.

✨ NEW Per-process Disk I/O and Private memory columns
▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔

  between samples, the same way the top-strip Disk graph works). Shows
